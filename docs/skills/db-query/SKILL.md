# 数据库查询（db-query）

## 何时使用

当用户的问题**答案只能是数据库里的数字或明细**时使用，例如：

- 「上周新增了多少用户 / 各店铺的订单量排名 / 最近 7 天每天多少会话」；
- 「这个 Agent 最近哪几个工具调用失败最多」「哪些平台还没绑定知识库」；
- 「找一下标题里带 XX 的任务」「上次那条报错的内容是什么」。

不需要查库的情况，别为了用工具而查：用户问的是**怎么操作**（去点哪个页面）、**配置在哪**、或你已经有工具直接回答（订单走 `order_query`、知识库走 `knowledge_search`、任务列表走任务工具）。查库是兜底手段，不是首选。

## 取数方式（先看结构，再查数）

1. **先 `db_schema`**：不熟悉的表必须先看，不要靠表名猜列名。只查几张表时传 `tables` 缩小范围；返回里有列类型和**中文备注**，它们决定你怎么理解字段。
2. **再 `db_query`**：写一条 `SELECT`（可用 `WITH`），拿真实结果。查询结果为空或数字可疑时，回头核对结构（是不是过滤条件写错、是不是该 JOIN 的表没关联上）。
3. 结构已经明确、且只是换个条件再查一次时，可以跳过第一步直接查。

## 写 SQL 的约定

- **只写一条 `SELECT` 或 `WITH ... SELECT`**。`INSERT/UPDATE/DELETE/DDL/GRANT/SET` 一律不支持——数据库角色与只读事务会直接拒绝，不要尝试绕过。
- **不要自己写 `LIMIT`**：工具会在外层套上限（默认 200 行）并在返回里告诉你 `truncated`。确实只需要几条时就传 `max_rows`，比写 `LIMIT` 更明确。
- **不要写 `WHERE platform_id = ...`**：行级策略已经按当前平台过滤，你写不写都一样，写错了反而会查出空结果。同理不要 `JOIN platforms` 来限定平台。
- **时间列都是 `timestamptz`**（`created_at`、`updated_at` 等），按北京时间理解；`date_trunc('day', created_at)` 这类按天聚合是常用手法，时区需要显式写 `AT TIME ZONE 'Asia/Shanghai'`。
- **列名是物理列名**（`platform_id`、`agent_id`、`created_at`），中文含义看 `db_schema` 返回的列备注。
- **大文本列先量再用**：`instruction_template`、`content`、`body` 这类 `text` 列可能很长，先 `length()` 或 `substr(col, 1, 200)`，不要整列拉出来。
- **优先聚合**：「有多少」「每天多少」用 `count/sum/group by` 直接算，比拉明细再自己数便宜也更准。
- 枚举/状态列（`status`、`role`、`channel`）取值不确定时，先 `SELECT DISTINCT col` 看一遍再统计，别假设取值。

## 输出规范

- **先给结论，再给依据**：第一句是数字或判断（「最近 7 天新增 128 个终端用户」），后面才是明细/分组表。
- 说清口径：时间范围、统计的是哪张表、有没有过滤（例如「只算已完成的运行」）。
- 结果被截断（`truncated=true`）时**必须说明**「这里只展示了前 N 行」，并给出继续看的办法（加过滤、换聚合、调大 `max_rows`）。
- 数字类结果不要贴原始 epoch 秒或 UUID 堆，时间转成 `YYYY-MM-DD HH:mm:ss`（北京时间）。
- 查不到就说查不到，并说明是「没有符合条件的数据」还是「条件可能写得太严」，不要编造数字。

## 错误处理

工具返回的是稳定错误码 + 一句短消息，按码处理：

- `db_reader_not_configured`：查库能力尚未开通（没有配置只读连接串）。如实告诉用户「数据库查询未开通，请联系管理员」，不要改用别的工具猜数字。
- `db_sql_rejected`：SQL 被规则拦下（非 SELECT、多语句、危险函数、语法问题）。按消息里指出的问题改写，**最多重试两次**；仍被拒就说明「这条查询当前不支持」，不要反复试探规则边界。
- `db_timeout`：查询超时。缩小时间范围、加更具体的过滤、或改成聚合查询再试一次。
- `db_result_too_large`：结果太大。少选几列、加过滤条件、分页/分段查。
- `db_error`：数据库侧执行错误（列名写错、类型不匹配等）。看短消息修正 SQL 后重试一次；仍失败就如实告知用户查询失败。

## 边界

- **只读**：本技能不做任何写入、修改、删除、建表、授权操作；用户要求写数据时如实说明不支持，并指出去后台页面操作。
- **单平台**：只能看到当前平台的数据；跨平台、跨租户的排查不在范围内，也不要用系统表/凭据表取巧。
- **不要展示敏感字段**：用户表里的密码哈希、token、密钥类字段即使能查到也不输出；依赖库层策略把它们挡住是正常的，查不到不要绕。
- 查库结果是**事实**，不是建议：基于结果回答，不要用推测补齐缺失的行。
