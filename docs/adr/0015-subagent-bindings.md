# 子智能体绑定：可派范围由父 Agent 显式配置，未配置回退全平台，并允许自克隆父配置差遣临时子运行

## Status

accepted（2026-10-21）

关联 Harness request：`docs/harness/requests/2026-10-21-subagent-bindings/spec.md`（tier A）。本 ADR 修订 `docs/adr/0005-delegated-subagent-runtime.md` 中「可派智能体 = 同平台 + 已发布、不新增白名单表」的结论，并补充子运行用量的计量口径；ADR 0005 其余结论（单个 `delegate_tasks`、深度恒 1、工具范围收缩、上下文完全隔离、父子事件不混流）不变。

## Decision

**可派范围由父 Agent 的显式绑定清单决定；未配置任何绑定时回退「本平台全部已发布 Agent（排除父自己）」。** 产品要的是「后台配好谁能被派」，而 ADR 0005 当时把「同平台已发布」当作 v1 收敛面、把白名单视为代价过高。现在需求已明确配置化，且候选收窄还顺带解决「模型在同一平台几十个 Agent 里乱选」的问题。回退而不是空清单，是为了让存量 Agent 升级后行为不变；「禁止委派」的总开关仍是「有没有绑定 `delegate_tasks` 工具」，不新增第二层开关。

**绑定是 agents 之间的 N:N 关联，不引入新的聚合根。** 新表 `agent_subagents` 只有父子两端、顺序与启用位；用途由子 Agent 自己的 name/description 表达，不另配。独立 teams 表会与既有版本、发布、工具绑定三套机制重复。

**保留单个 `delegate_tasks` 工具；`agent` 省略即自克隆父 Agent 配置，并可用 `role` 追加系统提示。** 每子智能体一个动态工具会让工具数量随配置膨胀，且要二次改造动态工具目录与授权模型。自克隆解决「没有配置子智能体 / 没有合适的现成子智能体」时无法干活的问题——它等价于 Pi 的 general-purpose worker 兜底，但不需要管理员先建一个通用 Agent。自克隆子运行与绑定子运行走同一条无人值守入口，唯一差异是目标 Agent 与可选的 role 段落；工具收缩、深度闸、新会话、无父上下文全部照旧。

**子运行用量写入既有 `model_usage_records`，且只对委派子运行开启。** ADR 0005 明确「子 token 不并入父 usage」，本次不改合并口径；但完全不可见的成本不可接受，所以子运行结束后按既有表结构记一条明细，读侧按子会话聚合给 delegatedRuns。任务、工作流链路不开启，避免顺手改变既有统计口径。

## Considered Options

- **每子智能体一个动态工具（`delegate_to_<slug>`）**：模型面更像团队，但工具数量与描述注入随配置增长，绑定/授权模型要二次改造。
- **独立 team / 子智能体聚合根**：父子只是 agents 之间 N:N，独立聚合根与既有版本、发布、工具绑定重复。
- **无绑定即禁止派发**：存量已绑工具的 Agent 升级后突然失去委派能力；而委派总开关已由工具绑定表达。
- **新增 `agents.delegation_scope`（all/bound）显式开关**：与工具绑定形成双重开关，多一列迁移却没有新增表达力。
- **`agent: "__self__"` 保留字或 `use_self` 布尔**：多一个模型要记的保留字/参数，易与真实 slug 混淆。
- **绑定关系配用途/别名**：子 Agent 自己的 name + description 是唯一事实来源。
- **允许跨平台绑定**：子运行跑在父平台的身份与会话上下文里，跨平台破坏多租户边界。
- **本次一并做子运行提问 + 事件直播**：ADR 0005 已否决父子混流；本次需求明确不需要。
- **新建 `delegated_runs` 表**：`agent_loop_runs` 已有父子列与 `run_metadata`，用量用既有 `model_usage_records` 聚合即可。
- **在 `execute_chat` 统一写用量**：embed 路径已由网关写，统一会双写并改变现有统计口径。
