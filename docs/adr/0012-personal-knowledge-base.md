# 个人知识库的属主与检索边界

## Status

withdrawn（2026-10-26：对应 request 已取消，方案未实施；本 ADR 保留为设计记录，不作为现行约束）

关联 Harness request：`docs/harness/requests/2026-10-20-personal-knowledge-base/`（tier A，spec 见该目录，`status: cancelled`）。
术语（知识库、公共知识库、个人知识库、会话主体）见 `CONTEXT.md`。
本 ADR 只回答一件事：把「个人信息」放进知识库并让它在对话里生效时，可见性由什么决定、边界落在哪一层。

## Decision

1. **属主挂在 `knowledge_bases` 上，用 `owner_type` + `owner_user_id` 两列表达，不新建表族。** 文档、分块、入库任务、引用构造全部以 `knowledge_base_id` 为锚，另立 `personal_knowledge_*` 表族意味着整条入库与检索管线复制一套并长期双写；本平台个人库量级只有「每平台几十成员 × 每人几库」，隔离带来的收益抵不上维护成本。
2. **可见性判据是「会话主体」，不是「请求发起人的角色」。** `conversations` 上已有 `ck_conversations_exactly_one_principal` 约束把发起者限定为 `user_id` XOR `platform_end_user_id`，这就是现成的主体概念，不需要发明新抽象；个人库的归属与它对齐。
3. **过滤下压到仓储层单一入口 `list_effective_for_agent_and_owner(agent_id, platform_id, *, owner_user_id)`，任何调用方都必须显式传主体。** 靠调用点各自过滤，漏改一处就是静默泄漏且无 SQL 可保证；把「Agent 绑定的公共库 ∪ 主体本人的个人库」写成一条查询，调用方没有表达「全部库」的方式。
4. **漏传主体时退化为「只有公共库」，而不是「全部库」。** 与 PostgreSQL RLS「未声明策略即默认拒绝」同一取向：默认分支必须是最小可见集。无人值守运行（任务、工作流）因此天然只检索公共库——没有在场的人，就没有可判定的主体。
5. **个人库不能被绑定到 Agent，绑定端点显式拒绝 `owner_type != 'platform'`。** 绑定的语义是「对该 Agent 的所有会话可见」，与个人库的定义直接冲突；靠约定不绑，一次误配就是不会报错的泄漏，所以必须由服务端拒绝而不是文档提醒。
6. **个人库的 embedding 配置引用 `platform_models`（`model_type='embedding'`），不沿用内联的 model/base_url/api_key 三要素。** 成员不该为了用私人资料自备模型密钥；引用还能让维度在建库时由后端探测一次落库，避免手填维度导致后续 `validate_embedding_dimension` 失败。公共库的内联字段保持原样，不回填、不迁移。
7. **文档子资源复用现有端点，只在 `get_base` 增属主校验分支。** 为个人库复制一套上传/列表/删除接口，会让两条文档管线的 chunk 与入库任务语义逐渐分叉；校验集中在一处，非属主一律 404（不泄露存在性，与现有 `_require_admin` 口径一致）。
8. **管理面新增 `/platforms/{pid}/me/knowledge-bases`，「我」由 `current_user.id` 强制决定，不接受客户端传 `user_id`。** 个人库也不出现在平台知识库列表与 Agent 绑定候选里；两者的目录语义不同，混在一个列表里迟早被误绑。
9. **平台管理员可读他人个人库的内容，但只读，且页面与接口都写明这一点。** 这是产品选择而非遗漏：当前能登录后台并对话的人本身就是 `platform_admins` 成员，本期个人库隔离的是「同一平台内不同成员」，不是「平台运营方看不到内容」。正因为如此，本轮也不做内容加密——在管理员可读的前提下加密没有隐私收益。真正的「运营方不可读」要等终端用户（`owner_type='end_user'`）侧接入。
10. **同一 embedding 配置的多个库共用一次 query embedding。** 原实现逐库调用 `aget_query_embedding`，个人库引入后调用次数随库数线性增长，必须收口为按 `(embedding_model_id, embedding_model, embedding_base_url)` 分组。
11. **个人库的文档内容不做按属主的磁盘隔离。** 沿用现有 `storage_path` 落盘约定，文件系统层面的隔离留待确有需要时再议；本期边界在数据库与应用层，写在这里是为了让后来者知道这是已知缺口而不是疏忽。

## Considered Options

1. **个人库也按普通库建、靠约定不绑到公共 Agent** ——零代码改动，但误配不会报错，且「绑定即全平台可见」的语义无法从数据上区分。
2. **个人库另立表族** ——隔离最直观、查询无需过滤，但入库与检索管线双写，且 `IngestionTask`、`KnowledgeChunk` 的向量检索代码要复制。
3. **属主直接复用 `platform_end_users`，一步到位支持终端用户** ——需要同时新建 embed 侧管理接口与鉴权，范围翻倍，而本期没有终端用户要管理知识库；改为保留 `owner_type` 枚举扩展点。
4. **每人自填 embedding 的 model/base_url/api_key** ——成员被迫各自持有模型密钥，密钥散落且维度靠手填；这也是方案 6 的反面。
5. **检索时先取全部库、再在应用层按属主过滤** ——查询简单，但安全性依赖每个调用点都记得过滤；可行性上等于把不变式交给自觉。
6. **个人库内容加密存储（应用级密钥）** ——在「平台管理员可读」的产品前提下不产生隐私收益，却引入密钥丢失即数据不可恢复的失败模式。
7. **无人值守运行注入发起人的个人库** ——「发起人」是给定时任务配置的人，不等于每次运行时的在场者；注入等于把私人内容交给后台任务。
8. **本轮顺带做长期记忆（从对话自动抽取事实存入个人库）** ——与「用户主动放的资料」抢同一个库，还需要抽取、去重、遗忘策略；独立请求。
9. **把个人信息做成一段「用户档案」注入系统提示，不建库** ——零基础设施，但只能承载几百字、无法上传文件、无法给出引用来源；作为方案 C 被否。
10. **在检索结果里区分「公共/个人」来源** ——对用户透明度更好，但要改引用卡片与 `Citation` 契约；本轮不做，留待个人库真正被日常使用后再评估。

## Consequences

- 单次对话的检索耗时随「Agent 绑定的公共库数 + 本人的个人库数」线性增长（每库一次向量检索）；query embedding 已按配置复用，剩余成本在向量检索本身。
- `owner_type` 目前只有 `platform` 与 `user` 两个取值；接入终端用户时需要扩枚举、加 embed 侧管理与鉴权，并确认 `owner_user_id` 与 `platform_end_user_id` 的列归属（当前设计假定属主是 `sys_users`）。
- 个人库与公共库在引用卡片上暂无来源差异，用户看不出某条引用来自自己的资料还是平台资料。
- 管理员读取他人个人库只打结构化日志，不落审计表（本期不建通用审计表）；需要合规级审计时要另外补。
- 「个人库」不等于「不可被他人看到」：同一平台的 `platform_admins` 成员可以通过管理端只读入口看到内容。这个边界必须在产品文案里说清楚，否则用户会误以为它是私密的。
