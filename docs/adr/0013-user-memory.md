# 用户记忆：不注入内容的按需记忆

## Status

accepted

关联 Harness request：`docs/harness/requests/2026-10-20-user-memory/`（tier A，spec 与验证证据见该目录）。
术语（用户记忆、记忆事实、记忆经历）见 `CONTEXT.md`。
本 ADR 回答两个问题：个人信息为什么不能放知识库，以及记忆为什么不默认注入上下文。

## Decision

1. **记忆与知识库是两套机制，不是一个库的两种配置。** 知识库解决「我有哪些资料」——长文档、切块、语义检索、命中才注入；记忆解决「我是谁、我干过什么」——短条目、按 key 覆盖、问到才查。把事实塞进知识库的失败点在检索：`retrieval_threshold` 默认 0.5、`retrieval_top_k` 默认 5，「我叫什么」这种四个字的问句与「姓名：李一」的向量距离没有任何保证，命中不了就等于没有记住；而改一条事实还得删文档重建索引。
2. **单表 `user_memories` 用 `kind` 区分事实与经历，不拆两张表。** 两者的差别只在写入语义（事实按 key 关闭旧行，经历只追加），读取、权限、删除、页面完全一致。拆表会把「查我的记忆」变成两个工具调用，模型少调一个就漏一半。
3. **事实带有效期，覆盖 = 关闭旧行而不是改写。** 每行有 `occurred_at`（开始时间）与 `valid_until`（结束时间，`NULL` 表示当前有效）；「我搬到上海了」写入新行并把「城市=北京」那行的 `valid_until` 置为当前时间。用户明确要求「必须加上时间，不然不知道我以前干了什么事」——静默覆盖会让「我以前住哪」永久不可回答。
4. **「同 key 同时只有一条有效事实」由部分唯一索引保证，不做应用层检查。** `uq_user_memories_active_fact (platform_id, user_id, key) WHERE kind='fact' AND valid_until IS NULL`。应用层先查再写会在并发下写出两条有效事实，而记忆的正确性正是这套系统的全部价值所在。
5. **记忆内容不注入上下文，只注入一行元信息。** 每次请求注入「当前用户已保存 N 条个人记忆（事实 x / 经历 y）」与使用规则，不含任何事实值。用户明确要求「不注入，只在询问时查找」；这一行元信息的作用是把「你有记忆可用」变成每次都在模型眼前的提示，否则「我叫什么」这类问句下模型很可能直接说不知道或编造。
6. **检索用「全量 active 返回 + 可选关键词过滤」，不做向量检索。** 量级是几十到两百条，全量返回不会漏且完全确定；向量检索要引入 embedding 配置、维度校验与「检索没命中」的新失败模式，在这个量级上只有成本没有收益。
7. **写入分 `explicit` 与 `inferred` 两种模式，自动写入受代码级白名单与敏感类别限制。** 用户说「记住」时 `explicit`，任意 key 任意内容；模型自行判定时 `inferred`，只允许事实类、只允许白名单 key（姓名/称呼/城市/时区/语言/工作角色/长期项目/明确偏好/忌讳），健康、财务、证件、政治、宗教、性取向、家庭关系等敏感类别一律拒绝并要求用户明示。校验写在服务层而不是只写在提示词里——提示词是建议，代码才是边界。
8. **经历类只能显式写入。** 经历是只追加的，写错了无法被后一条"覆盖"掉，只能在时间线上留下一段假历史；自动抽取的误记成本在这里是不可逆的。
9. **「本人范围写入」直通工具审批闸口，用显式白名单常量而不是把副作用伪报成 `none`。** `side_effect` 的取值是 MCP、宿主工具与前端共享的词汇表，伪报会让审批闸口对所有层失真；正确做法是在闸口处列出 `SELF_SCOPED_WRITE_TOOLS` 并附注释说明豁免理由，由单测锁定集合内容。豁免的代价用四件事补偿：写入后回显（「已记住：城市 = 上海（原值：北京）」）、条目可删除、覆盖可回滚（旧行仍在）、自动写入受第 7 条限制。
10. **`forget` 是物理删除，覆盖产生的历史行保留。** 「忘记」若只打标记，隐私语义上不诚实；而覆盖产生的旧行是用户要的时间线，必须留。两者的区别由「用户主动要求遗忘」与「信息自然过期」界定，删除只记 id 与时间到日志，不记内容。
11. **记忆按主体隔离，跨所有 Agent 共享；管理员只能看到条数与更新时间。** 用户要的是「不管在哪个窗口问都知道」，按 Agent 拆分会让同一事实在另一个 Agent 面前消失。管理员不可读内容是与知识库相反的口径：档案是对 AI 说的私话，且是短文本，管理不需要内容。
12. **无人值守运行既不注入索引也不能写记忆。** 没有在场主体，注入等于把私人内容交给定时任务，写入等于把任务配置者的猜测固化成用户事实。

## Considered Options

1. **全量注入记忆内容** —— 模型无须判断是否要查，命中率最高；但每轮吃 token，且用户明确否决了「注入」。
2. **把记忆做成知识库里的一个特殊库** —— 复用 embedding 与检索管线；但短事实的语义检索命中率不稳定，改一条事实要重建索引，且用户已判断个人信息不该做成知识库。
3. **自由文本档案块（模型维护一段 Markdown 注入）** —— 实现最轻；但「忘掉某一条」只能让模型重写整段，重写会顺手改掉别的条目，且无法给出时间线。
4. **事实与经历分两张表** —— 语义最清晰；但查询变两个工具、页面变两套、权限分支变两份。
5. **记忆做向量检索** —— 语义泛化更好（「公司」能匹配「上班的地方」）；但在这个量级上收益小于新增的配置面与失败面。
6. **后台自动抽取候选事实（pending → 用户确认）** —— 长期看是正确方向；但本期会翻倍范围，且必须配审核 UI 才能避免误记污染。
7. **写入弹审批确认卡** —— 复用既有审批机制、零例外；但每句「记一下」弹一次，记忆功能会被用户关掉。
8. **`forget` 软删（打标记）** —— 可恢复；但「忘记」不真删，隐私承诺就是假的。
9. **记忆按 (主体, Agent) 隔离** —— 工作 Agent 与私人 Agent 记忆分开，隔离更细；但与「不管在哪个窗口」的直觉冲突，且用户搭的 Agent 大多是自己的。
10. **管理员可读记忆内容** —— 与知识库口径统一；但短文本的个人私话不需要内容就能管理，统一口径在这里是过度暴露。

## Consequences

- **最大的残余风险是「模型该查而不查」**：索引行与提示词规则只是提高概率，无法根除；实测应记录「问个人信息但未调用 `memory_search`」的会话，作为后续调优输入。
- 没有向量检索意味着同义表述查不到（记「公司：字节」而后问「我在哪上班」），只能靠写入时在 `content` 里带上常见说法，或后续补关键词同义表。
- 事实的旧行会持续累积（每次变更一条），长期需要归档策略；本期只保证查询默认只看 active。
- `inferred` 写入的误记是可见的（回显 + 页面），但用户若没看回显，错误事实会一直生效直到下次纠正；白名单与敏感拦截把伤害面限制在「低风险类别 + 可回滚」。
- 记忆与个人知识库是两个独立请求：本 ADR 不改变知识库的属主与检索边界设计。
