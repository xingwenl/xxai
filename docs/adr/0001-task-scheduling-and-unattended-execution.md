# 任务调度采用独立容器 + 数据库抢占，无人值守执行走进程内 service 入口

## Status

accepted

## Decision

任务的调度不放进 API 进程，也不使用 Celery beat，而是新增一个常驻调度容器：到期时间落在 `tasks.next_run_at` 上，调度进程通过数据库行级锁抢占到期任务（`FOR UPDATE SKIP LOCKED`）并推进下一次触发时间。任务到点后的 Agent 运行不走 HTTP 自调用，也不引入新的机器身份 token，而是在调度进程内直接调用 conversation 模块的 service 入口，并以任务配置的执行身份（用户或平台主体）作为运行主体。

## Considered Options

- **Celery beat**：仓库已有 broker 与 worker 容器，看似最省事。但 Celery 官方文档明确要求同一时刻只能运行一个 scheduler，否则会产生重复任务——beat 是单点，而在本功能里重复触发意味着重复的模型调用与重复的会话。同时现有 Celery 只服务知识库，把调度混进去会让职责发散。
- **FastAPI 进程内的 asyncio 定时循环**：改动最小，但与 API 进程同生命周期，多副本必然重复触发，API 重启即中断调度。
- **复用微信机器人式的纯内存轮询**：触发时间没有持久化，重启即丢失，也无法表达「错过」语义。
- **worker 通过内部 REST 自调用并复用微信绑定式的 service token**：能复用现成鉴权，但会把「机器身份」引入权限模型，而本阶段明确只对平台管理员 JWT 开放接口。

## Consequences

- 多了一个常驻容器与一类新的部署单元；调度精度取决于 tick 间隔，不是硬实时。
- 调度天然支持多副本与重启恢复，不需要额外协调组件。
- 无人值守执行入口会以「用户或平台主体」的身份出现在既有会话与审计链路里，因此会话的可见性、执行记录与工具审计都需要能区分「这次运行由任务发起」。
- 任务运行的超时与失败清理必须由调度进程自己负责——本仓库在会话侧没有任何兜底的运行超时清理，进程被杀会留下永久 `running` 记录。
