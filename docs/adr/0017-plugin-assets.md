# 插件资产：二进制存文件、正文存同源路径

## Status

accepted

关联 Harness request：`docs/harness/requests/2026-10-25-plugin-assets/`（tier A，spec 与验证证据见该目录）。
术语（插件资产、plugin-assets、资产 key）见 `CONTEXT.md`。
本 ADR 只回答一件事：子应用的图片等二进制文件放在哪、怎么被引用、谁能写谁能读、什么时候回收。

## Decision

1. **二进制与 JSON 分家：新增 `plugin-assets` 存储根 `~/.desktop-app/plugin-assets/<pluginId>/`，不塞进 `plugin-data`。** plugin-data 是「每个 key 一个 `<key>.json`、单值 256 KiB」的小数据底座；截图一张 1~3 MB，base64 内联还要按 4/3 膨胀，且每次自动保存都要重写全部图片字节。分家后 JSON 与文件各自有清晰配额，人工排查也是一眼区分。
2. **资产 key 由服务端按内容生成：`sha256(data)[:16]` + 由 MIME 决定的扩展名，客户端不参与命名。** 一条决定同时解决三件事——文件名不可被客户端操纵（无路径穿越、无重名）、同图重复粘贴天然去重、key 与内容绑定因此可以放心长缓存。
3. **类型白名单只有 png/jpeg/webp/gif，并校验文件魔数而不是只信 Content-Type（OWASP File Upload Cheat Sheet 取向）。** 显式排除 svg：同源 SVG 可以携带脚本，直接打开就等于给宿主开 XSS 口子；位图类型没有这个能力。
4. **配额写死在存储层：单文件 2 MiB、单插件 64 MiB 与 500 个文件；超限返回 413 并说明当前用量。** 客户端在粘贴时已把截图压到长边 ≤1600 的 WebP（约 200~400 KB），所以 2 MiB 不是常态门槛而是「有人塞了张原图」的兜底；宿主仍按原始字节校验，不信任客户端声明。
5. **写入/列表/删除要求「插件已启用 且 manifest 声明 `assets`」，读取（GET）只要求插件已知。** `<img src>` 无法自定义鉴权头，把读取也绑到权限上会让「停用插件 → 历史图片全 404」变成常态；代价是知道 key 的本地进程能读到图片，这在单用户本地宿主里属于已知缺口（与 plugin-data 一致的信任模型），写在这里是为了让后来者知道这是取舍而不是疏忽。
6. **引用形式是站内绝对路径 `/api/desktop/plugin-assets/<pluginId>/<key>`，不存宿主主机地址。** 子应用由宿主在 `/apps/<pluginId>/…` 下同源提供，站内路径在宿主内、`vite dev` 的 `/api` 代理下都成立；存 `http://127.0.0.1:8765/...` 会在换端口、换机器、别的窗口模式下全断，还把本地地址写进用户正文。
7. **读取响应带 `Cache-Control: public, max-age=31536000, immutable` 与 `X-Content-Type-Options: nosniff`。** key 与内容一一对应，缓存永远不会显示错图；`nosniff` 让声明的图片类型真正生效，避免浏览器把响应猜成 HTML 执行（MDN）。
8. **孤儿资产的回收责任在子应用，不在宿主：宿主提供 `list/delete`，删笔记与清空废纸篓时由子应用扫剩余正文引用回收。** 只有子应用知道自己把资产引用写进了哪份正文；宿主定时扫或按引用计数维护索引，一旦解析有 bug 就是静默丢图，风险远大于收益。
9. **正文不改写：AI 工具返回的正文与用户看到的一致，只在 `tools.json` 的 description 里说明「图片是本地资产路径，模型读不到像素」。** 把图片替换成「[图片] 描述」之类的占位会让模型与用户看到两份不一样的正文，后续基于正文的更新（`note_update_note` 整体替换）会把改写带回去。
10. **已知缺口写清楚**：本地 REST 无令牌鉴权（沿用 plugin-data 的现状）；资产目录不随插件卸载清理（沿用 plugin-data 的口径）；不做资产与笔记的强一致性事务——上传成功而插入正文失败时会留下一个孤儿文件，由第 8 条的回收逻辑在下次删除笔记时带走。

## Considered Options

1. base64 内联进笔记 JSON：零宿主动手，但 256 KiB 上限下三五张就满，且整份重写；否决。
2. 客户端 localStorage/IndexedDB + `blob:` URL：不落宿主数据目录、跨会话失效；否决。
3. 复用 `storage` 权限存二进制：权限粒度变粗；否决，新增 `assets`。
4. 客户端指定文件名作 key：重名/穿越/误删引用都要额外处理；否决。
5. 允许 svg，用沙箱或 `Content-Disposition` 兜底：收益只有一个图标场景，代价是多一条容易被绕过的隔离链；否决。
6. 宿主定时扫目录做 GC：引用关系只有子应用知道，静默丢图风险高；否决。

## Consequences

- 宿主多一个存储根与配额管理，`~/.desktop-app` 下要多备份一个目录；子应用卸载后资产仍在磁盘上，需要人工清理（与 plugin-data 同待遇）。
- 子应用必须自己维护「正文引用 ↔ 资产」的一致性：上传成功但插入正文失败会留孤儿文件，已有回收路径兜底。
- 「图片只在宿主内能看」成为明确边界：正文粘到别处只剩站内路径，这是不存绝对地址、不做图床的直接后果。
- 后续若真需要音视频/PDF，只需扩白名单与配额常量，key/引用/回收三条语义不变。
