# 端用户记忆：记忆主体的第二种形态

## Status

accepted

关联 Harness request：`docs/harness/requests/2026-10-21-end-user-memory/`（tier A，spec 与验证证据见该目录）。
本 ADR 是 `docs/adr/0013-user-memory.md` 的补充而不是推翻：0013 定下「事实/经历、不注入内容、按主体隔离、无人值守拒绝」，本 ADR 只回答「接入方页面的终端访客也能有记忆吗，主体记在谁头上」。

## Decision

1. **记忆主体有两种，不是一种。** 后台用户主体落在 `sys_users.id`；终端用户主体落在 `(platform_embed_clients.client_id, platform_end_users.id)`。后台内嵌助手与接入方页面的访客共用一套记忆表、一套写入校验、一套注入规则，只有「主体从哪来」不同。
2. **不做 Client 级共享记忆。** 一个 Client 一份记忆会让同一页面的访客互相看见彼此姓名；记忆的价值与隐私边界都建立在「这条属于某个人」上，共享等于把功能做成事故。
3. **用「主体类型化列 + CHECK 恰好一种」而不是多态 `principal_type/principal_id`。** 会话控制台已有 `principal_type` 的展示先例，但表结构上多态外键不可建：删用户后留下的 `principal_id` 既查不到归属也删不掉，与 0013 第 10 条「忘记即物理删除」冲突。因此 `user_id` 可空、`client_id` 与 `end_user_id` 成对出现，由 `CHECK` 与两条部分唯一索引（`... WHERE user_id IS NOT NULL` / `... WHERE end_user_id IS NOT NULL`）分别保证唯一。
4. **后台身份通过 Embed token 的可选 `user_id` 声明传递。** 只有服务端受信任入口 `GET /embed/agent-token`（已持有后台登录态）设置该声明；公开 `POST /embed/tokens` 永远不设。运行时 `decode_embed_token` 校验其存在时必须是整数，工具层据此选主体；没有声明的会话不可能伪装成后台用户。
5. **端用户主体按 Client 隔离，同一个人跨 Client 视为两个主体。** 不同接入站点之间没有共享的「同一个人」判断依据（`external_user_id` 由接入方赋值，两个 Client 的 `"1"` 可能是两个人）；合并比拆分更危险，拆分至少只是记不住。
6. **无人值守与无主体会话继续拒绝记忆工具。** 沿用 0013 第 12 条与 `memory_principal_required` 错误码；端用户主体是「在场的聊天对象」，无人值守不是。
7. **端用户会话补一行记忆索引。** 0013 第 5 条要求「每次请求注入条数」，但当时的实现只覆盖 REST 后台用户路径；端侧提示词里从来没有这一行，等于工具存在但模型不知道。本次按主体计数注入，仍只含条数、不含内容。
8. **端用户记忆不进管理台。** 0013 第 11 条「管理员只看条数与更新时间」的前提是「记忆有后台本人可对照」；第三方访客没有后台账号，做列表等于让平台管理员读接入方的用户隐私。只在会话内可读写。
9. **不加 Client 级 `allow_end_user_memory` 开关。** 记忆是否可用已由 Agent 的 `builtin_tools` 配置决定（Agent 没挂记忆工具就调不到）；再叠一层 Client 开关，排查「为什么记不住」要多问一句「Agent 配了吗、Client 开了吗」，收益不成立。
10. **迁移只加列与索引，不重写存量记忆。** 存量行天然是后台用户主体（`user_id` 非空、端用户列全空），`downgrade` 时删除端用户行（不可逆点写在迁移 docstring 里）。
11. **Embed 会话的 `conversations.user_id` 保持为空。** 会话控制台按 `principal_type='end_user'` 展示，把后台用户声明写进会话行会让第三方访客在列表里被当成后台用户，也会让「后台用户自己的会话」统计口径失真。

## Considered Options

1. **只给受信任入口记忆（加 `user_id` 声明，终端访客继续拒绝）** —— 最小改动、无迁移；但接入方访客记不住，用户明确选了 Client + 终端用户隔离。
2. **多态主体列（`principal_type` + `principal_id`）** —— 列更少、与会话控制台表达统一；但无外键、孤儿记忆无法清理。
3. **Client 级共享记忆** —— 实现最省；但同 Client 访客串号。
4. **端用户记忆在管理台可见** —— 便于运营排查；但突破 0013 的隐私口径，且没有「本人」可授权。
5. **Client 级 `allow_end_user_memory` 开关** —— 给接入方显式授权；但能力已由 Agent 工具配置承载，双开关只增加解释成本。
6. **给 Embed 会话补 `conversations.user_id`** —— 让控制台直接看到后台用户；但会把第三方访客误标成后台用户。
7. **拆表/拆库按 Client 隔离** —— 隔离最硬；但迁移、查询、备份都是倍数级复杂度，本条用索引条件即可。

## Consequences

- 好处：后台浮动助手「记住我」立刻可用且管理台可见；接入方访客在不改 SDK、不改线协议的情况下获得按人隔离的记忆；两种主体共享写入校验与敏感类别约束，不需要维护第二套记忆逻辑。
- 代价：`user_memories` 多三列与两条部分唯一索引；记忆查询的所有入口都要传主体，仓储层签名改动会波及工具、路由与测试；`end_user_id` 外键删除级联意味着删端用户会静默删记忆（与隐私口径一致，但需要文档写明）。
- 待观察：端用户记忆没有管理台入口，出问题时只能看日志与会话；若接入方要求「访客能自己清空记忆」，需要补一个端侧工具或 SDK 能力，属于下一期。
