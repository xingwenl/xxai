# FastAPI 后端 Harness 规范

本文件约束 `apps/backend/` 下的后端任务如何在 Harness 流程内设计、实现、验证和验收。

## 适用范围

适用于以下场景：

- 新增 FastAPI 接口
- 修改已有路由、请求体、响应体
- 新增或调整 SQLAlchemy 模型
- 新增服务层、仓储层、配置项
- 修复后端 bug

## 后端任务的最小工作流

涉及 `apps/backend/` 的正式任务，默认按以下顺序推进：

1. 在 `docs/harness/requests/<request-id>/` 创建工作区
2. 在 `research.md` 调研 FastAPI 官方文档、成熟开源项目或相关生产实践
3. 基于调研结论，在 `spec.md` 写清目标、范围、风险、停点判断、验收标准
4. 在 `plan.md` 写清变更文件、实施步骤、测试步骤、回滚方案
5. 再进入代码实现
6. 在 `verify.md` 记录实际执行命令与实际结果
7. 在 `acceptance.md` 给出验收结论与剩余风险

## 推荐目录边界

当后端需求开始增多时，优先保持以下边界清晰：

- `main.py`：应用入口与启动对象
- `app/api/`：路由层，负责 HTTP 输入输出
- `app/schemas/`：Pydantic 请求体、响应体模型
- `app/services/`：业务编排与规则
- `app/repositories/`：数据库访问封装
- `app/models/`：SQLAlchemy 模型
- `app/core/`：配置、日志、数据库连接、公共基础设施
- `tests/`：按 API 或业务边界组织测试

如果当前项目规模还小，可以先不一次性拆全，但新增逻辑时要尽量避免把所有代码继续堆在 `main.py`。

## 分层职责

### 路由层

负责：

- 定义路径、HTTP 方法、状态码
- 接收并校验请求参数
- 调用服务层
- 返回响应体

不应负责：

- 直接写复杂业务逻辑
- 到处散落数据库访问
- 把内部异常原样暴露给调用方

### 服务层

负责：

- 编排用例
- 聚合多个仓储或领域对象
- 承载业务规则
- 决定错误语义

不应负责：

- 直接耦合 FastAPI 的 `Request`、`Response`
- 在服务内部拼接 HTTP 响应结构

### 仓储层

负责：

- 读写数据库
- 隔离查询细节
- 为服务层提供明确的数据访问接口

不应负责：

- 承担业务编排
- 把事务边界写得分散不可控

## Spec 阶段必须回答的问题

后端 request 的 `spec.md` 至少要写清：

- 这个接口或模块解决什么问题
- 谁会调用它
- 输入是什么
- 输出是什么
- 是否改动数据模型
- 是否改动 API 契约
- 是否改动鉴权或权限
- 回归风险落在哪些已有接口或流程
- 方案基于哪些业界调研结论
- 为什么选择当前方案，而不是调研过的其他方案

## Research 阶段必须回答的问题

- 这个功能在业界有哪些成熟实现
- 官方文档或权威来源推荐什么做法
- 参考方案的适用条件、收益和限制是什么
- 本项目的约束是否适合直接采用
- 最终选择什么方案，哪些方案明确不采用，原因是什么

调研记录必须包含来源链接、版本或发布日期和调研日期。不能只写“业界通常如此”或直接复制某个项目的实现。

如果以下任一答案为“是”，必须等待人工确认：

- 需要新增或修改数据表、字段、实体关系
- 需要新增或修改公开 API 契约
- 需要新增或修改登录、鉴权、权限校验语义
- 需要改变服务职责边界或模块边界

## Plan 阶段建议写法

后端任务的 `plan.md` 建议至少包含：

- 变更文件清单
- 数据流说明
- 每一步实现顺序
- 测试命令
- 回滚方式
- 人工确认点

推荐把步骤写成“先定义接口边界，再补 schema，再补 service/repository，再补测试”的顺序，避免先写散乱实现，后补设计。

## Verify 阶段最低要求

`verify.md` 不能只写“已测试通过”，至少要记录：

- 执行命令
- 预期结果
- 实际结果
- 失败项与例外

FastAPI 任务常见验证命令示例：

- `poetry run pytest`
- `poetry run pytest tests/path/to/test_file.py -q`
- `poetry run ruff check .`
- `poetry run black --check .`
- `poetry run uvicorn main:app --reload`

如果因为仓库尚未补齐测试文件、脚本或环境而无法运行，也必须明确写在 `verify.md` 中，不能跳过不记。

## Acceptance 阶段最低要求

`acceptance.md` 至少要回答：

- 当前是否达到 spec 的验收标准
- 哪些验证已经完成
- 还有哪些风险没有消除
- 是否还需要人工回归或联调

如果只是“文档工程”类后端任务，也要明确写出“本次未涉及运行时行为变更”。

## FastAPI 代码约定

### 接口设计

- 路径命名保持资源化，避免动作堆叠
- 请求体、响应体使用 Pydantic 明确定义
- 响应结构要稳定，不要随手返回裸字典造成契约漂移

### 配置管理

- 环境变量统一收口到配置层，不要在各处直接 `os.getenv`
- `.env` 仅用于本地开发，不要把秘密值写入仓库

### 数据访问

- SQLAlchemy 模型、会话管理、查询逻辑不要和路由层混写
- 在 `models.py` 定义表结构时，每个字段都必须通过 ORM/数据库字段定义的 `comment` 元数据添加清晰的中文备注，说明字段含义或用途
- 涉及事务时，在 plan 中明确事务边界

### 代码注释

- 后端代码应根据逻辑复杂度和维护需要增加必要的中文注释
- 注释重点说明业务意图、关键约束或非直观实现原因，避免无意义的逐行翻译式注释

### 错误处理

- 对外错误语义要稳定
- 预期内业务错误应转成明确的 HTTP 状态码和响应信息
- 非预期异常应避免泄露内部细节

## 推荐 request 类型

### 1. 纯接口新增

适用于：

- 新增健康检查接口
- 新增简单查询接口

通常不需要审批，但仍要走完整 Harness 阶段。

### 2. 数据模型变更

适用于：

- 新增表
- 新增字段
- 调整实体关系

必须在实现前等待人工确认。

### 3. API 契约变更

适用于：

- 修改请求体字段
- 修改响应体结构
- 修改状态码语义

必须在实现前等待人工确认。

### 4. 权限语义变更

适用于：

- 新增鉴权依赖
- 修改用户可访问资源范围

必须在实现前等待人工确认。

## 与 monorepo 的关系

虽然当前重点是 `apps/backend/`，但 request 仍统一放在仓库根目录的 `docs/harness/requests/` 下，不在后端目录内部再维护一套独立流程。

这样做的目的：

- 保持前后端任务规则一致
- 支持一个 request 同时覆盖接口、文档、前端联动
- 避免子目录各自发散出不同的工程纪律
