# 全局 Harness 策略

## 阶段

- research
- spec
- plan
- implement
- verify
- acceptance

## Request 状态

- `active`：request 仍在推进
- `done`：已完成验收，可以合并或归档
- `blocked`：因人工确认、外部依赖或环境问题无法继续

`phase` 表示当前工作阶段，`status` 表示 request 生命周期状态。`done` 和 `blocked` 不是阶段，不能写入 `phase`。

标准流转为：

```text
phase: research -> spec -> plan -> implement -> verify -> acceptance
status: active -> done
```

**spec 完成后的方案对齐检查点（强制）**：每次完成或更新 `spec.md`（含 `/modify`、`/fix` 的增量变更记录）后，必须先把方案要点（目标、范围、关键设计决策、停点判断）发给用户确认，用户确认后才能继续 `plan` 或进入实现；未确认前不得写实现代码。

如果无法继续，保留当前 `phase`，将 `status` 设为 `blocked`，并在 `verify.md` 或 `acceptance.md` 记录阻塞原因、已尝试动作和解除条件。

## Spec 增量变更规则

当一个需求在原有 `spec.md` 基础上继续追加功能，且仍属于同一任务闭环时，可以复用原 request，不必强制新建 request。

但必须同时满足以下条件：

- 变更仍服务于原始目标，不形成新的独立子项目
- 变更没有跨出原任务的核心业务边界
- 原有 `research`、`spec`、`plan`、`verify`、`acceptance` 仍适合作为同一闭环继续维护

若复用原 request，必须执行以下要求：

- 在 `spec.md` 中维护 `## 变更记录`
- 每次变更按时间倒序追加一条记录
- 每条记录至少包含：变更时间、变更原因、变更内容、影响章节、是否触发人工确认
- 若变更影响 `范围`、`风险`、`停点判断`、`验收标准`，必须同步更新正文，而不是只写在变更记录里
- 若变更影响实施方式、测试步骤或回滚说明，必须同步更新 `plan.md`
- 若变更影响验证预期，必须同步更新 `verify.md`
- 若变更触发新的人工确认条件，必须先完成确认，再进入实现或继续推进
- 复用增量同样受「spec 后方案对齐检查点」约束：变更记录落定后先把本次变更点发给用户确认，再进入实现
- 若本次属于 bug 修复，也必须写入 `变更记录`，推荐将记录类型标注为 `fix`

以下情况不得继续复用原 request，必须新建 request：

- 变更已经形成新的独立需求闭环
- 变更目标与原 `spec` 目标不再一致
- 变更累计过多，导致原 `spec` 已难以表达当前真实设计边界

推荐的变更记录格式：

```md
## 变更记录

### 2026-06-02 第 1 次变更

- 变更原因：补充需求或修正设计假设
- 变更内容：说明本次新增或调整的功能点
- 影响章节：范围、风险、验收标准
- 是否触发人工确认：否
- 关联计划更新：已同步更新 `plan.md`
```

## 轻量模式

对于仍属于已有 request 闭环的小功能、小修正、小 bug，可以使用轻量模式，避免每次都按完整大流程扩写大量文档。

### 适用条件

同时满足以下条件时，可以进入轻量模式：

- 已经存在可复用的 request
- 改动仍属于原 `spec` 目标闭环
- 不新增独立子项目或独立验收主题
- 不触发以下高风险变更：
  - 架构变更
  - 数据模型变更
  - API 契约变更
  - 鉴权或权限变更
- 对聊天相关任务，不触发聊天专项审批条件

### 典型适用场景

- 现有 spec 内的小功能补充
- 不改变接口或数据结构的 bugfix
- UI 微调、交互微调、提示文案调整
- 已有实现中的小范围逻辑修正

### 轻量模式最低要求

进入轻量模式后，仍必须保留最小 Harness 痕迹：

- 使用已有 request 的增量入口
- 在原 `spec.md` 的 `## 变更记录` 中补一条简短记录
- 把本次变更点发给用户确认后再写实现代码（「spec 后方案对齐检查点」同样适用，变更点极小时可随变更记录一并确认）
- 若实施步骤、验证预期、验收结论受影响，只更新必要段落，不要求重写整份文档
- 在 `verify.md` 中补充本次实际执行过的最小验证
- 在 `acceptance.md` 中补一句本次轻量变更的结论或结果

轻量模式不要求重新创建 `research.md`，但出现以下情况时必须补充调研结论：

- 修复方案发生变化
- 新增范围需要比较不同实现方案
- 涉及性能、安全、可靠性或外部依赖

### 轻量模式下允许的简化

- 不要求新开 request
- 不要求重写完整 `plan.md`
- 不要求扩写大量风险分析，只需在变更记录中说明本次影响面
- 若验收边界未变化，可只增量更新 `verify.md` / `acceptance.md`

### 必须升级回标准模式的情况

出现以下任一情况，必须退出轻量模式，回到标准 Harness 流程：

- 改动已经超出原 `spec` 目标
- 形成新的独立功能闭环
- 需要修改数据模型、接口契约、权限规则、架构边界
- 聊天相关改动触发专项审批条件
- 无法清晰说明“本次只是原 spec 的小增量”

## Skills 调用规范

当执行 `/new`、`/modify` 或 `/fix` 时，AI 必须先做复杂度评估，再决定技能调用策略。本仓库使用的技能来自 mattpocock/skills，安装在 `~/.agents/skills/`；引用某个技能时，读取并遵守其 `SKILL.md`，若技能未安装则按对应完成判据内联执行，不阻塞流程。

### 策略 A：轻量级变更

触发条件：

- 修改文案、样式
- 修改单一函数、单一组件的局部逻辑
- 增加非核心字段
- 已有 spec 范围内的小功能补充
- 不改变接口、数据结构、权限语义的小 bug 修复

执行动作：

- 不调用外部技能
- 直接读取旧 `spec.md`
- 先写 `变更记录`
- 同步补最小必要文档
- 仅增量更新 `plan.md` / `verify.md` 必要段落

### 策略 B：复杂 / 架构级变更

触发条件：

- 数据库表结构或实体关系变更
- 新增核心业务模块
- 跨多个服务、页面、组件的联动修改
- 鉴权逻辑、权限规则、API 契约、架构边界重构
- AI 无法明确判断复杂度或影响面

执行动作（按序完成，满足完成判据才进入下一步）：

1. 调研：调用 `research` 技能收集业界依据，结论写入 `research.md`。
   完成判据：`research.md` 包含来源、方案比较和最终决策。
2. 梳理上下文：读取相关 request 的 research/spec/plan、专项规范（backend.md / frontend.md）与相关代码目录。
   完成判据：能说清现状、约束与影响面。
3. 方案拷问（按 `meta.json` 的 `riskLevel` 分级）：
   - `high` 或命中审批四条件：读取并遵守 `grill-with-docs`（路由到 `grilling` 拷问方案、`domain-modeling` 沉淀 ADR 与术语），完成判据：方案被逐条拷问，被否决的选项与理由已记录
   - `medium`：`grilling` 可选调用，以第 6 步用户确认为主
   - `low`：不调用拷问技能
4. 领域文档克制：ADR 只在跨 request、影响后续开发的架构决策时写入 `docs/adr/`（首次需要时创建）；`CONTEXT.md` 术语表只在出现反复使用且易混淆的领域术语时创建；平时的方案比较与不选原因写入 `spec.md` 即可，不为每个 request 新建 ADR。涉及模块或接口设计时，结合 `codebase-design` 的深模块词汇。
5. 设计不确定时：调用 `prototype` 技能先做一次性原型，验证关键设计问题。
6. 未决点澄清：必要时向用户提问，确认方案方向。
7. 输出或更新 `spec.md`：记录方案比较与不选原因。
8. 编写 `plan.md`：按 `templates/plan-template.md` 直接写入当前 request 工作区（`docs/harness/requests/<request-id>/plan.md`），不调用 `writing-plans`，不写入 `docs/superpowers/plans/`。

### 实现与验证阶段（可选技能）

- `implement`：按 spec 实现，建议在明确的接缝处使用 `/tdd`
- `diagnosing-bugs`：`/fix` 遇到难以定位的问题时先诊断再修改
- `code-review`：`verify` 阶段对本次改动做规范与 spec 双轴评审，结论不能替代真实验证命令的记录

### 输出格式与落点规则

技能提供执行过程，不决定正式文档的格式与落点：

1. 六份正式产出（`research.md` / `spec.md` / `plan.md` / `verify.md` / `acceptance.md` / `meta.json`）以 `docs/harness/templates/` 为模板，写入 `docs/harness/requests/<request-id>/`；技能默认输出路径或格式与 Harness 冲突时，以 Harness 为准并显式覆盖（如 `research` 技能的结果写入 `research.md`，`plan.md` 一律按模板写，不采用技能的默认 plan 格式）。
2. 跨 request 的架构决策才写 `docs/adr/`（首次需要时创建）；术语表写根目录 `CONTEXT.md`（按需创建）；交接文档写 `docs/handoff/`。
3. 一次性产出不进 request 工作区：原型按 `prototype` 技能默认用临时分支或临时目录，诊断笔记与评审草稿不落正式文档，结论提炼后写入 `verify.md` / `acceptance.md`。
4. AI 不得自创目录承载 Harness 正式产出（如 `docs/superpowers/`）；确需新目录时先向用户确认。
5. 正式文档使用中文；代码、命令、路径、字段名可保留英文。
6. 调用技能前先确认其产出物：存在默认落点时先检查冲突，冲突则先覆盖再执行。

默认原则：

- 能明确归入轻量模式时，优先策略 A
- 只要存在明显的不确定性或高风险信号，升级为策略 B
- 分级依据创建 request 时写入 `meta.json` 的 `riskLevel`（low / medium / high）

## Research 调研规范

### 适用范围

- `/new` 创建的新功能、新模块或新接口族，必须完成 `research.md`
- `/modify` 如果改变方案、扩大范围或新增独立技术决策，必须补充或更新调研
- `/fix` 如果只是局部实现错误，可以不重新调研；如果改变方案或涉及性能、安全、可靠性，必须补充调研
- 普通概念问答、代码解释和不产生仓库变更的讨论不创建 request

### 来源质量

参考来源按优先级排列：

1. 官方文档、官方示例和标准规范
2. 维护活跃、使用广泛的成熟开源项目
3. 可信的生产实践、技术文章和事故复盘

不得只引用搜索摘要、无来源转载或“业界通常如此”这类无证据结论。小功能至少包含一个官方或权威来源和一个成熟案例；普通业务功能比较两到三种方案；核心功能增加安全、性能、可观测性或生产实践调研。所有来源都必须记录链接、版本或发布日期、调研日期。

### 调研结论

`research.md` 至少记录：调研问题、参考方案、适用条件、收益、限制、方案比较、最终选择和不选其他方案的原因。`spec.md` 必须引用 `research.md` 的关键结论；如果调研没有改变方案，也必须说明原因。

### 外部资料不可用

如果网络、权限或资料时效导致无法完成预期调研，不能假装调研已完成。必须在 `research.md` 记录：已尝试的来源、失败原因、采用的替代依据、剩余风险和后续补充条件。核心功能在关键资料缺失时，应暂停方案定稿并请求人工确认。

## 人工审批触发条件

- 架构变更
- 数据模型变更
- API 契约变更
- 鉴权或权限变更
- 核心功能缺少关键业界资料，无法可靠完成方案比较

人工确认应发生在 `research` 完成、`spec` 方案确定之后，且必须早于 `implement`。AI 可以在 `research` 阶段比较方案，但不能因为找到成熟案例就跳过确认直接实现。

## 阶段流转规则

request 必须按以下条件推进：

- `research -> spec`：调研结论、来源和方案比较已记录
- `spec -> plan`：目标、范围、方案、风险和验收标准已确定
- `plan -> implement`：计划已完成，且人工确认已通过或明确不需要
- `implement -> verify`：实现已完成，或明确记录本次只涉及文档/配置
- `verify -> acceptance`：验证记录包含真实命令、结果、失败项和例外
- `acceptance -> done`：验收标准全部满足，剩余风险已记录
- 任意阶段 -> `blocked`：存在明确的人工确认、外部依赖或环境阻塞

`meta.json.phase` 必须表示当前阶段，`meta.json.status` 必须表示当前生命周期状态；进入下一阶段前，应先补齐上一阶段的正式文档。

## 最低验收要求

- 列出变更文件
- 记录验证命令
- 总结验证结果
- 明确写出未解决问题

## 文档语言规则

- AI 生成的正式文档必须使用中文
- 代码、命令、路径、字段名可保留英文
