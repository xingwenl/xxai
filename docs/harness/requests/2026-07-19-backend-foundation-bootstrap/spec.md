# 设计说明

## 目标

- 建立后端第一阶段基础设施骨架，让后续业务模块可以直接复用统一配置、日志、数据库、异常、分页和响应规范。
- 把“分页查询”“固定返回格式”从口头约定变成共享代码能力。
- 通过一个最小系统模块验证基础设施装配方式可运行、可测试、可扩展。

## 范围

- 新建后端基础设施 request 工作区。
- 在 `apps/backend/` 下补齐：
  - 应用工厂与路由装配
  - `core/config.py`
  - `core/logging.py`
  - `core/database.py`
  - `core/security.py`
  - `shared/base_model.py`
  - `shared/exceptions.py`
  - `shared/responses.py`
  - `shared/pagination.py`
  - 最小 `system` 模块与健康检查接口
  - 对应最小测试
- 更新 `pyproject.toml`，声明基础设施依赖。

## 非目标

- 本次不实现用户、订单等真实业务模块。
- 本次不建立具体业务表结构和 Alembic migration 版本文件。
- 本次不确定最终鉴权实现。
- 本次不接入缓存、消息队列、任务调度等更重基础设施。

## 风险

- 固定返回格式属于后续接口契约基线，若后面要改，将产生全局改造成本。
- 当前环境若未安装新增依赖，只能完成“代码与结构”层验证，不能完成真实数据库连通验证。
- 分页模型如果设计得过重，会增加简单查询接口的样板代码。

## 停点判断

- 是否涉及架构边界变化：否，本次落实的是已确认的后端基础架构。
- 是否涉及数据模型变化：否，本次只建立 ORM 基类和数据库入口，不引入业务表。
- 是否涉及 API 契约变化：是，会新增健康检查接口，并定义统一成功/失败返回格式与分页元信息基线。
- 是否涉及鉴权或权限行为变化：否。
- 结论：本次范围来自用户在 2026-07-19 的明确继续指令，可直接推进实现，并在验收中记录契约基线。

## 验收标准

- `apps/backend/` 下形成可读的基础设施目录骨架。
- 存在统一配置、日志和数据库会话入口。
- 存在统一成功/失败返回格式模型与分页参数/元信息模型。
- 存在至少一个最小健康检查接口，作为基础设施装配验证样例。
- 存在仓库内可直接执行的数据库建表脚本，统一走 Alembic migration。
- 存在最小自动化测试，验证共享响应或分页能力。
- request 文档完整记录 research、spec、plan、verify、acceptance。
