# 业界调研记录

## 调研问题

- 在已经确认 `FastAPI + PostgreSQL + SQLAlchemy 2.0 async + Alembic` 的前提下，第一阶段后端基础设施应优先落哪些能力。
- 固定返回格式、分页查询、日志、配置和数据库基建，哪些应该作为第一阶段的共用地基一起做。

## 功能复杂度

- 级别：核心功能
- 选择理由：本次会建立后续所有后端模块共同依赖的基础设施和接口规范，影响目录边界、API 返回约定和开发节奏。
- 最低调研要求：官方文档 + 成熟案例 + 明确范围收敛。

## 方案比较

| 方案 | 优点 | 限制 | 与本项目的匹配度 |
|---|---|---|---|
| 方案 A：先只做数据库和日志，分页/返回格式等以后再补 | 短期启动快 | 后续接口很容易各写各的，返工成本高 | 中 |
| 方案 B：第一阶段同时搭配置、日志、数据库、统一异常、固定返回格式、分页能力、最小健康模块 | 先把横切能力收口，后续业务开发可直接复用 | 初期代码会略多，但边界更清晰 | 高 |
| 方案 C：先直接写用户模块，在开发中自然抽公共层 | 看起来贴近业务 | 公共能力会在业务开发中反复重构 | 低 |

## 最终决策

- 选择方案：方案 B。
- 选择原因：
  - 这批能力都是后续接口都会反复使用的横切基础设施。
  - 固定返回格式和分页若不先定，后面最容易出现风格漂移。
  - 用一个最小系统模块验证地基是否顺手，比直接上业务模块更稳。
- 不选择其他方案的原因：
  - 不选方案 A：会把分页、异常和返回格式的规范债推到后面。
  - 不选方案 C：公共基础在业务里边写边抽，成本更高。
- 对后续 spec、plan 或人工确认的影响：
  - 本次会引入新的基础代码目录、公共响应契约与健康检查接口。
  - 用户已在 2026-07-19 明确要求继续推进后端基础设施，并点名关注分页和固定返回格式，可视为本次基线范围已获确认。

## 剩余风险

- 资料时效性：官方文档来源为 2026-07-19 可访问版本。
- 与本项目上下文的差异：成熟模板通常自带完整鉴权和部署链路，本次会刻意收敛为“第一阶段地基”。
- 尚未验证的假设：
  - 当前本地环境尚未安装 `asyncpg`、`alembic` 时，数据库连接链路无法做完整连通验证。
