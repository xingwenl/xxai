# Phase 2B 宿主页面工具业界调研记录

## 调研问题

本 request 需要让 Agent 在严格授权后请求第三方页面执行宿主工具，并支持用户确认、结果回传、幂等和审计。调研重点是：

- 如何避免浏览器注册工具扩大后端授权范围；
- 如何在后端与 SDK 之间保持 JSON Schema 校验语义一致；
- 如何设计有副作用工具的确认、执行、超时和断线状态；
- 如何保证重复消息或重连不会造成重复副作用；
- 如何在现有 `ai-agent.v1` WebSocket、MCP 工具和审计体系中保持模块边界清晰。

本功能属于核心功能，影响数据模型、WebSocket API、权限语义、浏览器执行边界和审计事实。

## 参考依据

### 来源 1：Model Context Protocol Tools 规范

- 类型：官方协议规范。
- 名称：Model Context Protocol - Tools。
- 链接：https://modelcontextprotocol.io/specification/2025-06-18/server/tools
- 版本或发布日期：2025-06-18 规范版本；调研日期：2026-07-28。
- 核心做法：工具由名称、描述和输入 JSON Schema 描述；调用方应校验工具名称和参数，工具结果使用结构化内容表达，错误需要和正常结果区分。
- 对本项目的启发：宿主工具沿用标准工具描述模型，但注册信息只作为页面能力声明；后端发布策略仍是授权源，不能由浏览器注册覆盖。

### 来源 2：JSON Schema Draft 2020-12

- 类型：官方规范。
- 名称：JSON Schema Draft 2020-12。
- 链接：https://json-schema.org/draft/2020-12
- 版本或发布日期：2022-06-16 发布；调研日期：2026-07-28。
- 核心做法：以标准 Schema 和验证词汇描述结构、类型、必填项、范围及组合约束；验证器应依据同一 Schema 解释输入。
- 对本项目的启发：后端保存并校验发布策略的 Schema，SDK 在发送注册和实际执行前再次校验，工具参数不使用无边界的自定义校验函数替代 Schema。

### 来源 3：Ajv JSON Schema Validator

- 类型：成熟开源项目官方文档。
- 名称：Ajv 8。
- 链接：https://ajv.js.org/json-schema.html
- 版本或发布日期：Ajv 8 文档，支持 JSON Schema 2020-12；调研日期：2026-07-28。
- 核心做法：浏览器侧使用标准 Draft 2020-12 验证 JSON 数据，编译 Schema 后复用验证器，并明确不同 draft 不能混用同一个实例。
- 对本项目的启发：SDK 使用显式的 2020-12 validator；注册时和执行时都限制 Schema 与参数大小，错误以稳定协议错误返回。

### 来源 4：Stripe Idempotent Requests

- 类型：成熟生产实践官方文档。
- 名称：Stripe API Idempotent Requests。
- 链接：https://docs.stripe.com/api/idempotent_requests
- 版本或发布日期：当前在线文档；调研日期：2026-07-28。
- 核心做法：客户端为可能重试的请求提供唯一 idempotency key，服务端记录首次结果并对相同 key 返回同一结果；同一 key 不应复用不同参数。
- 对本项目的启发：每个宿主调用使用不可预测的 `callId`，服务端以主体、Agent 和工具上下文绑定 callId 与参数摘要；重复结果只能沿用原调用状态，不能再次请求页面执行。

### 来源 5：OWASP WebSocket Security Cheat Sheet

- 类型：权威安全实践。
- 名称：WebSocket Security Cheat Sheet。
- 链接：https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html
- 版本或发布日期：当前在线版本；调研日期：2026-07-28。
- 核心做法：握手和每条业务消息都要做授权；限制消息大小、连接生命周期和速率；记录安全相关事件；不信任客户端声明。
- 对本项目的启发：`host_tools_register`、`host_tool_result`、`host_tool_error` 和 `confirmation_resolve` 都必须按当前 embed token 主体重新授权，不能只依赖连接认证或浏览器提交的 `platformId`。

## 方案比较

| 方案 | 做法 | 优点 | 限制 | 匹配度 |
|---|---|---|---|---|
| A：后端授权、浏览器执行 | 后端保存宿主工具策略并计算三重白名单交集；SDK 注册真实函数；后端发送 `host_tool_call`，SDK 校验并执行后回传结果 | 符合浏览器安全边界；页面业务能力不离开浏览器；策略、状态和审计集中在服务端 | 需要新增策略、调用状态、确认和审计模型；需要处理断线与超时 | 高，推荐 |
| B：后端代理执行 | 页面把工具实现注册到后端或让后端执行同名服务工具 | 服务端可统一重试和审计；连接协议较简单 | 无法安全获得页面内存和 DOM 业务上下文；容易退化为任意脚本或后端重复实现 | 低 |
| C：浏览器自行决定执行 | 后端仅发送工具名和参数，页面自行判断是否允许并执行 | 实现简单，页面自由度高 | 客户端可伪造结果或绕过后台白名单；授权、确认和审计不可信 | 不采用 |

## 最终决策

- 选择方案 A：后端权威授权与状态机、SDK 本地执行。
- 工具可调用集合固定为：`token 允许工具 ∩ Agent 发布策略 ∩ 当前页面已注册工具`。注册不扩大 token 或 Agent 策略权限。
- 后端为宿主工具建立独立策略、调用和审计模型，不复用 MCP 审计表；MCP 仍由现有 MCP 执行链处理。
- `none` 工具可按策略自动执行；`navigation`、`write`、`financial`、`external` 默认进入 `awaiting_confirmation`。确认由当前页面最终用户通过 WebSocket 解决，后端使用原子状态更新防止重复批准。
- 调用状态采用 `requested -> awaiting_confirmation -> running -> succeeded|failed|rejected|expired`。页面断线时不自动重试副作用调用；服务端按 `callId` 返回已有最终状态或过期状态。
- SDK 执行必须有 `AbortSignal`、超时、结果大小限制和敏感字段过滤；不能执行任意 JavaScript、`eval`、任意 DOM 操作或未注册函数。
- 对已有 2A 的影响仅限协议扩展和网关调用编排；需要新增数据库迁移、独立 router/service/repository/model、SDK registry/transport 测试和审计查询能力。

## 不选择其他方案的原因

- 不采用后端代理执行：页面工具的价值在于访问当前页面的业务上下文，后端无法安全替代；同时会扩大服务端执行边界。
- 不采用浏览器自行决定执行：浏览器属于不可信执行端，不能决定后台允许哪些 Agent/工具，也不能成为审计事实源。
- 不把宿主工具并入 MCP 表：MCP 工具和宿主工具的执行位置、凭据边界、主体模型和失败语义不同，混表会导致权限与审计查询混淆。
- 不用仅内存状态：进程重启或多实例会丢失调用事实，重复结果可能触发重复副作用；数据库保存调用最终状态，Redis 只承担连接事件转发或短期通知。

## 对 spec、plan 和人工确认的影响

- 必须新增宿主工具策略、调用状态和独立审计数据模型及迁移。
- 必须扩展 `ai-agent.v1` 客户端/服务端事件契约，并对注册、调用、结果、错误和确认事件做主体级授权。
- 必须新增平台管理员配置 API，修改 Agent 的宿主工具能力范围。
- 必须获得人工确认后才能进入实现，确认范围包括数据模型、API 契约、WebSocket 权限语义和 SDK 执行边界。

## 剩余风险

- 页面函数本身可能执行不可逆业务操作，SDK 只能限制调用协议，不能替代接入方页面自身的业务授权和 CSRF 防护。
- 浏览器断线与工具实际执行之间可能出现结果已产生但回传丢失的窗口；必须以 `callId` 查询最终状态并禁止盲目重试。
- “敏感字段过滤”需要明确字段名规则和结果递归遍历策略，默认应采用保守拒绝或脱敏，而不是依赖模型判断。
- 现有 SDK 测试基础设施和真实浏览器 E2E 覆盖仍需在实现阶段补齐。
