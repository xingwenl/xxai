# 知识库管理业界调研记录

## 调研问题

- 如何在现有平台级 FastAPI 模块上补齐知识库管理闭环？
- 文档上传、URL 抓取、异步切分向量化和失败重试应如何向管理前端暴露？
- 如何避免前端继续依赖旧的 `/api/knowledge-bases` 契约？

## 功能复杂度

- 级别：普通业务功能，包含 API 契约、异步任务状态和文件生命周期。
- 选择理由：本次不改变向量检索核心算法，但会增加资源列表、删除、重试和平台权限边界。
- 最低调研要求：一个官方向量数据库/摄取文档来源、一个成熟 Web 数据管理案例，并结合当前仓库实现比较方案。

- 对本项目的启发：管理 API 应围绕现有实体和任务实现补齐读取、删除和重试，不引入第二套导入管线。

## 现状差异

| 管理能力 | 当前后端 | 前端旧实现 | 本次需要 |
|---|---|---|---|
| 平台选择 | 有当前用户平台列表 | 未接入 | 接入 `/platforms` |
| 知识库列表 | 缺失 | 调用旧 `/api/knowledge-bases` | 新增平台级列表 |
| 创建/编辑 | 创建和 PATCH 已有 | 调用旧 PUT 契约 | 改用真实平台级契约 |
| 删除知识库 | 缺失 | 调用旧 DELETE | 新增硬删除 |
| 文档列表 | 缺失 | 调用旧分页接口 | 新增平台级列表 |
| 文件/URL 添加 | 已有 | 路径和请求体不匹配 | 对接真实接口 |
| 文档详情 | 已有 | 未形成列表管理 | 保留并用于刷新 |
| 文档删除/重试 | 缺失 | 调用旧全局接口 | 新增平台级接口 |
| 文本条目 | 当前模型无独立文本条目实体 | 旧前端保留 | 本次不实现，避免伪造契约 |

## 方案比较

| 方案 | 优点 | 限制 | 与本项目的匹配度 |
|---|---|---|---|
| 前端继续调用旧 `/api/...` 接口 | 改动少 | 当前后端没有对应契约，无法鉴权和联调 | 低，不采用 |
| 前端写死平台和只做创建上传 | 能快速展示页面 | 没有列表、删除、重试，无法形成管理闭环 | 低，不采用 |
| 补齐平台级后端契约，再实现前端 | 复用现有模块、权限校验和异步任务；可测试、可演进 | 需要新增 API 和定向测试 | 高，采用 |

## 最终决策

- 选择方案：以 `/platforms/{platform_id}/knowledge-bases` 为唯一管理边界，补齐列表、硬删除、文档列表、文档删除和文档重试接口，前端全部迁移到该契约。
- 选择原因：与现有智能体模块的管理模式一致，平台管理员校验集中在后端，且不破坏已有搜索、绑定和异步入库实现。
- 不选择其他方案的原因：旧接口无法映射当前数据库模型和权限；写死平台会制造隐性配置和越权风险。
- 对后续 spec、plan 或人工确认的影响：新增 API 契约和硬删除语义，进入实现前必须取得人工确认。

## 剩余风险

- 资料时效性：参考资料为在线文档，具体 API 版本以当前仓库依赖和实现为准。
- 与本项目上下文的差异：Qdrant/LangChain 是通用组件，本项目已有自定义 Celery 任务和 pgvector 结构。
- 尚未验证的假设：数据库外键级联在目标 PostgreSQL 环境已启用；Celery broker 可正常调度重试任务；上传文件删除时需要同步删除本地存储文件。
