# 业界调研记录

## 调研问题

- 在当前 `sys_users` 基础上，如何为用户引入“角色”概念，且后续可以稳定扩展到权限体系。
- 当需求包含“用户拥有自己的角色”和“可按角色查询用户”时，数据模型应该采用单角色还是多角色关系。
- 第一阶段应做到“角色资料管理 + 用户角色关联 + 按角色过滤用户”的什么边界，才能既可落地又不把权限体系一次性做过头。

## 功能复杂度

- 级别：核心功能
- 选择理由：本次会新增真实数据模型、用户与角色关系表、角色相关接口与列表查询能力，直接影响后续鉴权和后台管理边界。
- 最低调研要求：官方/权威 RBAC 资料 + 成熟框架实践 + 后续扩展影响分析。

## 参考依据

### 来源 1

- 类型：权威标准资料
- 名称：NIST RBAC FAQ
- 链接：https://csrc.nist.gov/Projects/role-based-access-control/faqs
- 版本或发布日期：在线资料，2026-07-20 访问
- 调研日期：2026-07-20
- 核心做法：RBAC 的核心关系是 user-role assignment 和 permission-role assignment；角色本身是稳定的业务职责抽象，用户通过角色获得能力。
- 对本项目的启发：当前第一阶段至少应采用“用户-角色”解耦建模，而不是把角色名直接塞进 `sys_users` 单字段里。

### 来源 2

- 类型：权威标准资料
- 名称：NIST IR 6192 - A Revised Model for Role Based Access Control
- 链接：https://csrc.nist.gov/pubs/ir/6192/final
- 版本或发布日期：1998-07-09
- 调研日期：2026-07-20
- 核心做法：核心 RBAC 以用户、角色、权限及其关系为基础；层级角色是可选增强，不是最小实现的前置条件。
- 对本项目的启发：第一阶段不必一上来做角色继承或复杂职责分离，先把 core RBAC 的用户-角色关系建稳更合适。

### 来源 3

- 类型：官方文档
- 名称：Django - Using the authentication system / Groups
- 链接：https://docs.djangoproject.com/en/3.2/topics/auth/default/
- 版本或发布日期：在线文档，2026-07-20 访问
- 调研日期：2026-07-20
- 核心做法：`User` 与 `Group` 采用多对多关系，用户可以属于多个组，组再承载权限。
- 对本项目的启发：如果已经预期后续会有“一个用户多个角色”的可能，优先使用关联表，而不是给 `sys_users` 增加单个 `role_id`。

### 来源 4

- 类型：官方文档
- 名称：Auth0 Docs - Role-Based Access Control
- 链接：https://auth0.com/docs/manage-users/access-control/rbac
- 版本或发布日期：在线文档，2026-07-20 访问
- 调研日期：2026-07-20
- 核心做法：角色是权限集合，推荐按职责分组，并坚持最小权限原则；用户可以被分配一个或多个角色。
- 对本项目的启发：本次 `sys_roles` 设计应避免把角色仅当成展示标签，至少要为未来挂权限保留稳定的 `code` 和职责语义。

### 来源 5

- 类型：官方文档
- 名称：Keycloak Server Administration Guide - Roles and Role Mappings
- 链接：https://www.keycloak.org/docs/latest/server_admin/
- 版本或发布日期：在线文档，2026-07-20 访问
- 调研日期：2026-07-20
- 核心做法：用户角色分配与角色实体分离；角色映射是独立管理动作，复合角色虽可用但不建议过早过度使用。
- 对本项目的启发：本次更适合先落“角色实体 + 用户角色关联”，把角色层级、复合角色留到后续 request。

## 方案比较

| 方案 | 优点 | 限制 | 与本项目的匹配度 |
|---|---|---|---|
| 方案 A：在 `sys_users` 增加单个 `role_id` | 实现最简单，查询也直观 | 无法表达多角色；后续扩展权限体系时容易推倒重来 | 中低 |
| 方案 B：新增 `sys_roles` 与 `sys_user_roles`，采用用户-角色多对多 | 与主流 RBAC 实践一致；支持一个用户多个角色；便于后续挂权限 | 需要多一张关联表，接口与查询实现稍复杂 | 高 |
| 方案 C：现在直接做到 `sys_roles + sys_permissions + sys_role_permissions + sys_user_roles` 全量 RBAC | 一次把未来鉴权体系全铺好 | 当前范围明显过大，会把权限、菜单、资源授权都拉进来 | 中低 |

## 最终决策

- 选择方案：方案 B。
- 选择原因：
  - 能满足“用户有自己的角色”与“根据角色查询用户”的当前需求。
  - 与 Django、Auth0、Keycloak 一类成熟实践更一致，后续接权限体系时不会卡在单角色模型上。
  - 把复杂度控制在“角色资料 + 用户角色关联 + 用户按角色过滤”这一层，不把权限系统一次性做满。
- 不选择其他方案的原因：
  - 不选方案 A：短期省事，但未来出现“一个用户多个角色”时会产生数据模型升级成本。
  - 不选方案 C：当前还没有明确的权限资源、菜单授权、接口授权边界，过早做全量 RBAC 容易失控。
- 对后续 spec、plan 或人工确认的影响：
  - 会新增 `sys_roles`、`sys_user_roles` 两张表，属于数据模型变化。
  - 会扩展用户创建/更新/详情/列表的对外契约，并可能新增角色管理接口，属于 API 契约变化。
  - 进入实现前必须再次获得人工确认。

## 剩余风险

- 资料时效性：本次参考的是 2026-07-20 可访问的官方文档与权威 RBAC 资料。
- 与本项目上下文的差异：成熟系统通常已经把权限、资源和组织层级一起做了；本次刻意收敛为角色基础层。
- 尚未验证的假设：
  - 当前业务是否确定“一个用户可拥有多个角色”；本设计按“支持多角色”处理。
  - 当前是否需要角色停用、角色删除保护、默认角色自动分配；这些可以在实现阶段再收敛。
