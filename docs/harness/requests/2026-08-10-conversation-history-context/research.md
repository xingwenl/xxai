# 业界调研记录

## 调研问题

本项目的 AI SDK 通过后端会话调用模型。需要确认历史消息应由 SDK 传递还是由后端按会话读取，以及如何限制历史上下文的时间范围。

## 功能复杂度

- 级别：普通业务功能
- 选择理由：涉及聊天核心上下文组装、数据库查询和模型调用链，但不新增数据表或公开 API 字段。
- 最低调研要求：官方对话上下文资料 + 一个成熟开源实现，并比较时间窗口、消息裁剪方案。

## 参考依据

### 来源 1

- 类型：官方文档
- 名称：OpenAI API 对话状态与消息上下文
- 链接：https://platform.openai.com/docs/guides/conversation-state
- 版本或发布日期：持续更新，调研时可用版本
- 调研日期：2026-08-10
- 核心做法：无托管会话状态时，应用需要在请求中传入此前消息；托管会话 ID 只是把状态保存职责交给服务端。
- 对本项目的启发：本项目已有后端会话持久化和 `conversation_id`，历史消息应由后端可信读取，SDK 不应重复提交可被篡改的完整历史。

### 来源 2

- 类型：成熟开源项目官方文档
- 名称：LangChain ConversationBufferWindowMemory
- 链接：https://python.langchain.com/docs/versions/migrating_memory/conversation_buffer_window_memory/
- 版本或发布日期：LangChain 文档，调研时可用版本
- 调研日期：2026-08-10
- 核心做法：将历史消息按窗口限制后再注入模型，保持消息顺序，并把当前输入作为最新消息。
- 对本项目的启发：保留后端持久化消息，查询时按时间截止点过滤并按时间正序传给 LangChain；时间窗口比 SDK 本地缓存更可靠。

## 方案比较

| 方案 | 优点 | 限制 | 与本项目的匹配度 |
|---|---|---|---|
| SDK 每次发送完整历史 | 实现直观，服务端查询少 | 历史可被客户端篡改，网络负载和隐私风险更高 | 低 |
| 后端按 `conversation_id` 查询最近时间窗口 | 身份边界可信，兼容 HTTP/SSE/SDK，集中控制成本 | 每轮增加一次数据库查询，需要索引 | 高 |
| 模型供应商托管 thread/conversation | 减少应用侧上下文拼装 | 强绑定供应商，无法统一数据库审计和多模型切换 | 中低 |

## 最终决策

- 选择方案：后端按会话读取最近时间窗口内的已完成消息，并在 `run_graph`/`stream_graph` 中注入。
- 选择原因：复用现有会话表和 `conversation_id`，不改变 SDK 与后端公开协议；默认 1 小时可通过环境变量配置。
- 不选择其他方案的原因：客户端历史不可信；供应商托管状态会削弱现有多模型和审计能力。
- 对后续 spec、plan 或人工确认的影响：仅修改服务、仓储、运行时和配置，不触发数据模型、API、鉴权或架构边界审批。

## 剩余风险

- 时间窗口只限制时间，不限制 token；极长消息仍可能造成上下文超限，后续可增加 token/字符预算。
- 多个并发请求可能读取到相同的旧历史，但不会改变消息归属；本次不处理并发轮次排序。
