# 设计说明

## 目标

- 为本仓库确定第一版后端基础技术方案，并沉淀成可长期复用的技术规范文档。
- 让后续 `apps/backend/` 下的新接口、新模块和数据库改动都能直接引用统一规范，而不是每次重新争论目录、ORM、迁移和配置方式。
- 基于 `research.md` 的结论，确定采用 `FastAPI + PostgreSQL + SQLAlchemy 2.0 async + Alembic`，并使用按领域模块划分的目录结构。

## 范围

- 新建本次 request 工作区，记录 `research -> spec -> plan`。
- 新增一份后端技术规范文档，明确：
  - 基础技术栈
  - 目录结构
  - 分层职责
  - 数据访问规范
  - 配置、日志、异常、测试和迁移规范
  - 当前已定项与待讨论项
- 本次涉及目录：
  - `docs/harness/requests/2026-07-19-backend-technical-spec/`
  - `docs/harness/specs/`

## 非目标

- 本次不实现业务接口。
- 本次不新增数据库表、字段或实体关系。
- 本次不确定具体鉴权方案，只定义预留边界。
- 本次不直接修改 `apps/backend/` 代码或依赖清单。

## 风险

- 这是架构边界层面的规范文档，一旦拍板，后续目录与依赖选型会围绕它展开，变更成本高于普通代码修正。
- 当前仓库后端代码仍很薄，规范若写得过重，会抬高初始实现成本；写得过轻，又会失去约束力。
- 数据库访问若后续在同步/异步之间摇摆，会导致 repository 和测试基建反复重写。

## 停点判断

- 是否涉及架构边界变化：是，本次确定后端的模块边界、数据访问模式和目录组织方式。
- 是否涉及数据模型变化：否，本次尚未落到具体业务表结构。
- 是否涉及 API 契约变化：否，本次尚未定义对外接口。
- 是否涉及鉴权或权限行为变化：否，本次只保留后续预留位。
- 结论：进入实现前需人工确认。

## 验收标准

- `research.md` 至少包含 5 个来源，并覆盖官方文档与成熟案例。
- `spec.md` 明确说明本次是架构级规范决策，并标出需要人工确认。
- 新增的后端技术规范文档能够回答以下问题：
  - 后端采用哪些核心技术
  - 模块目录如何组织
  - router/service/repository/model/schema 的职责边界是什么
  - 数据库连接、迁移、配置和测试如何落地
  - 哪些点已定，哪些点待你确认
- `plan.md` 能说明后续若进入实现，应按什么顺序推进。
