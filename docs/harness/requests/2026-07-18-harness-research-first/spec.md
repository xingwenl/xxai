# Harness 开发前业界调研

## 目标

- 将业界成熟案例调研纳入新功能的标准前置流程。
- 在确定实现方案前，优先参考官方文档、成熟开源项目和生产实践，减少重复讨论与闭门设计。
- 为每个新功能留下可追溯的调研依据、方案比较和最终决策。

## 范围

- 更新 `docs/harness/README.md`，将 `research` 放在 `spec` 之前，并定义调研阶段职责。
- 更新 `docs/harness/backend.md`，补充 FastAPI 后端新功能的调研要求。
- 新增 `docs/harness/templates/research-template.md`，作为新 request 的调研记录模板。
- 更新 spec、plan、meta 模板以及 Golden Path 和 FastAPI 示例。
- 建立本 request 的完整调研、实施、验证和验收记录。

## 非目标

- 不为本次规则变更新增搜索服务、自动化脚本或外部数据源。
- 不修改 `apps/backend/` 的运行时代码、API、数据模型或权限行为。
- 不要求所有简单问题都创建调研报告；本规则针对新功能 request，普通概念问答仍使用直接对话。

## 业界调研要求

### 调研对象

优先级按以下顺序排列：

1. 官方文档、官方示例和标准规范
2. 维护活跃、使用广泛的成熟开源项目
3. 可信的生产实践、技术文章和事故复盘

### 最低产物

每个新功能 request 必须在进入方案定稿前记录：

- 调研问题与功能背景
- 至少一个官方或权威来源
- 参考方案的核心做法
- 方案的适用条件、收益和限制
- 我们选择的方案及不选其他方案的原因
- 来源链接、版本或发布日期、调研日期

### 按复杂度分级

- 小功能：官方文档加一个成熟案例，记录简短结论。
- 普通业务功能：比较两到三种方案，记录关键取舍。
- 核心功能：补充开源项目、生产实践、安全性、可观测性或性能方面的对比。

调研深度不足时，必须在 `research.md` 中说明原因和剩余风险，不能用“业界通常如此”替代证据。

## 风险

- 资料版本可能过期，需要记录版本或发布日期和调研日期。
- 开源项目的上下文可能与本项目不同，不能直接照搬实现。
- 外部资料结论可能不完整，核心功能仍需要结合本项目约束验证。

当前未识别到高风险运行时变更。

## 停点判断

- 是否涉及架构边界变化：否
- 是否涉及数据模型变化：否
- 是否涉及 API 契约变化：否
- 是否涉及鉴权或权限行为变化：否
- 本次为 Harness 文档和流程变更，不需要进入实现前人工确认。

## 验收标准

- `docs/harness/README.md` 明确写出 `research -> spec -> plan -> implement -> verify -> acceptance`。
- 新 request 模板包含 `research.md`，并要求记录来源和方案决策。
- FastAPI 规则明确要求新增功能先完成业界调研。
- Golden Path 示例体现先调研、后定 spec 和 plan 的顺序。
- 本 request 的 `research.md`、`verify.md` 和 `acceptance.md` 记录实际内容，且不存在未处理的占位符。
- 不改动 `apps/backend/` 运行时代码。
