# 设计说明

## 目标

- 为 FastAPI 后端增加本地文件日志能力，解决当前只有控制台日志、无法在本地文件中持续查看运行日志的问题。
- 受影响对象为后端开发者、运维排查人员，以及所有通过 `app.core.logging.get_logger` 获取 logger 的后端模块。
- 完成后，调用 `setup_logging` 后写入的日志应同时输出到控制台和本地日志文件，并支持按日期滚动保留历史文件。
- 根据 `research.md` 结论，本次采用 Python 标准库 `logging.config.dictConfig` 与轻量自定义 `DatedFileHandler`，不引入第三方日志库。

## 范围

- 修改 `apps/backend/app/core/config.py`，增加日志文件相关配置项。
- 修改 `apps/backend/app/core/logging.py`，增加日志目录创建、滚动文件 handler 和可配置参数。
- 修改 `apps/backend/app/__init__.py`，在应用启动时把日志文件配置传入 `setup_logging`。
- 增加 `apps/backend/tests/system/test_logging.py`，验证配置生成、目录创建、文件写入和滚动 handler 参数。
- 增加 `.gitignore` 忽略本地生成的日志文件，避免运行日志进入版本控制。

## 非目标

- 不新增日志查询 API 或前端日志查看页面。
- 不新增数据库日志表，不持久化业务日志到数据库。
- 不接入 ELK、Loki、OpenTelemetry 等集中式日志或可观测性平台。
- 不改变业务模块现有 `get_logger(__name__)` 的调用方式。
- 不强制接管 Uvicorn access log 或容器平台日志采集策略。

## 风险

- 日志文件路径配置错误时可能导致启动阶段创建目录失败，本次通过默认路径和测试覆盖降低风险。
- 文件日志会占用磁盘空间，本次通过 `LOG_FILE_BACKUP_COUNT` 控制保留份数；若单日日志量很大，后续可再引入集中式日志或大小加时间组合策略。
- 多进程同时写同一天日志文件时，文件并发写入和归档清理仍需按部署方式单独评估；当前本地开发和单进程服务场景可接受。
- 当前未识别到高风险业务运行时变更。

## 停点判断

- 是否涉及架构边界变化：否。本次只增强已有核心日志工具，不新增服务边界。
- 是否涉及数据模型变化：否。
- 是否涉及 API 契约变化：否。
- 是否涉及鉴权或权限行为变化：否。
- 结论：不触发进入实现前的额外人工审批。

## 验收标准

- `setup_logging` 默认配置包含 console 和 file 两个 handler。
- 默认日志文件路径为 `apps/backend/logs/app.log`，并在目录不存在时自动创建。
- 日志文件 handler 使用 `app.core.logging.DatedFileHandler`，当前活跃文件应直接写入 `app-YYYY-MM-DD.log`，并支持配置基础日志文件路径和保留份数。
- `get_logger(__name__)` 的既有调用方式不变，业务代码不需要迁移。
- 测试覆盖配置生成、目录创建和日志实际写入文件。
- 验证记录中包含真实执行过的测试命令和结果。
