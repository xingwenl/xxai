# 技能管理业界调研记录

## 调研问题

- 如何把已有平台级 Skill 模型接成可用的后台管理闭环？
- 技能模板、参数 schema、生命周期 hooks 和智能体绑定应如何展示和变更？
- 停用与删除如何影响运行时加载？

## 功能复杂度

- 级别：普通业务功能，涉及配置 CRUD、运行时启用语义和多对多绑定。
- 选择理由：不新增表结构，但会改变管理 API 契约和删除操作，且技能会直接进入会话系统提示词。

## 现状差异

| 管理能力 | 当前后端 | 本次需要 |
|---|---|---|
| 平台选择 | 已有当前用户平台列表 | 前端接入 |
| 技能列表 | 缺失 | 新增分页列表 |
| 创建技能 | 已有 | 前端对接 |
| 编辑技能 | 缺失 | 新增 PATCH |
| 启用/停用 | 只有模型字段，无接口 | 复用 PATCH |
| 删除技能 | 缺失 | 新增硬删除 |
| 绑定智能体 | 已有 PUT | 前端接入 |
| 查询绑定 | 缺失 | 新增按智能体查询 |
| 解绑 | 缺失 | 新增 DELETE |

## 方案比较

| 方案 | 优点 | 限制 | 与本项目的匹配度 |
|---|---|---|---|
| 继续调用旧 `/api/skills` | 表面改动少 | 当前后端没有该契约，无法平台鉴权 | 低，不采用 |
| 只做技能 CRUD | 实现快 | 无法管理技能实际绑定对象，运营闭环不完整 | 中，不作为最终方案 |
| 平台级 CRUD + 智能体绑定/解绑 | 与现有 runtime 和 agent 页面一致，权限边界清晰 | 需要新增 API 和绑定交互 | 高，采用 |

## 最终决策

- 选择方案：新增平台级技能列表、更新、硬删除、智能体绑定列表和解绑接口；保留创建和绑定接口。
- 停用语义：更新 `is_active=false`，不删除绑定，运行时立即不加载。
- 删除语义：硬删除技能，数据库级联删除 `agent_skills` 绑定。
- 前端：新增 `/ai/skills` 页面，支持平台选择、技能 CRUD、启停、硬删除和选择智能体绑定。
- 不选择旧接口的原因：旧前端类型描述的是另一套上传式 Skill Package 模型，与当前后端 `Skill` 实体不一致。

## 剩余风险

- JSON schema 和 hooks 的业务校验当前由 Pydantic 只保证对象形状，复杂 JSON Schema 合法性留给后续专项校验。
- 硬删除不可恢复，页面需二次确认。
- 真实会话是否即时读取停用状态需要数据库和服务联调确认。
